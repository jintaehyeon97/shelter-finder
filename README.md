# 🌡️ 폭염 안전 지도 (Heatwave Safety Map)

폭염 시 현재 위치 기준으로 주변 편의점·무더위쉼터를 지도에서 찾고, 태양 위치 기반 그늘 추정과 실시간으로 갱신되는 도보/대중교통 경로를 안내해주는 위치 기반 안전 지원 앱입니다.

React Native(Expo) 앱과 Node.js/Express 백엔드로 구성된 풀스택 개인 프로젝트입니다.

---

## 배경

폭염이 심해지는 여름, 밖에 있을 때 가장 가까운 그늘/쉼터가 어디인지 빠르게 알기 어렵다는 문제의식에서 시작했습니다. 처음엔 "편의점 재고 확인 앱"으로 기획했지만, 개발 과정에서 실제로 더 필요한 건 "폭염 상황에서 안전하게 대피할 곳을 찾는 것"이라고 판단해 방향을 전환했습니다.

## 핵심 기능

- 🗺️ **전국 편의점 + 무더위쉼터 지도** — 카테고리별 필터 토글
- 📍 **현재 위치 기반 반경 검색** — 편의점은 카카오 로컬 API 실시간 조회, 쉼터는 PostGIS 공간 쿼리
- 🔍 **통합 검색 / 거리순 추천 리스트**
- 🌡️ **실시간 기온 표시** — 기상청 초단기실황 API
- 🧭 **도보·대중교통 경로 안내** — 실시간 위치 갱신에 따라 경로 자동 재계산
- 🌳 **그늘 경로 추정** — 태양 고도·방위각을 직접 계산해 건물 그림자가 도로를 덮을 가능성을 추정하고, 경로를 그늘/노출 구간으로 색칠. 슬라이더로 최대 3시간 뒤까지 그늘 변화를 미리 볼 수 있음

## 배포

- 백엔드: [Render](https://render.com) (무료 티어)
- DB: [Supabase](https://supabase.com) PostgreSQL + PostGIS (무료 티어)
- API 상태 확인: https://shelter-finder-pjjk.onrender.com/health

> 프론트엔드는 앱스토어 배포 없이 Expo Go로 실행합니다 (개인 테스트/포트폴리오 목적).

## 기술적으로 흥미로웠던 문제들

### 1. 좌표계를 잘못 짚어서 편의점이 전부 바다 밖으로 튀었던 문제
공공데이터의 좌표값을 보고 "당연히 국내에서 흔히 쓰는 좌표계(EPSG:5179)겠지"라고 가정하고 변환했는데, 결과가 전부 한국 밖으로 튀어나갔습니다. 좌표값의 크기를 직접 계산해보니 실제로는 지도 서비스들이 흔히 쓰는 **Web Mercator(EPSG:3857)** 좌표였고, 변환 공식을 바꾸자 바로 정상으로 돌아왔습니다. 이후로는 좌표를 변환할 때마다 "결과가 진짜 한국 범위 안에 들어오는지" 자동으로 검증하는 로직을 추가했습니다.

### 2. 지도 앱에서 마커가 사라지지 않고 흐릿하게 남는 버그 (Android)
필터를 껐다 켰을 때, 또는 같은 경로를 다시 요청했을 때, 지도 위 마커나 경로선이 제대로 안 지워지고 흐릿하게 겹쳐 보이는 현상이 있었습니다. 원인을 찾아보니, 화면을 그려주는 라이브러리(React)가 "완전히 새로 그리기" 대신 "기존 것에 살짝 덧칠하기" 방식으로 처리할 때, Android 쪽 지도 엔진이 이걸 제대로 못 따라가는 문제였습니다. 매번 고유한 번호를 붙여서 "이건 완전히 새로운 것"이라고 강제로 알려주는 방식으로 해결했습니다.

### 3. 그늘 데이터가 없어서, 태양의 위치를 직접 계산해 그늘을 추정
"그늘이 많은 경로"를 추천하고 싶었는데, 국내엔 "이 도로가 그늘진다"는 데이터 자체가 없었습니다. 그래서 발상을 바꿔서, 시간과 위치만 알면 계산 가능한 **태양의 위치(하늘의 어느 방향에, 얼마나 높이 떠 있는지)**를 직접 계산했습니다. 그리고 "도로 방향"과 "태양 방향"을 비교해서, 두 방향이 수직에 가까울수록(= 태양이 옆에서 도로를 비출수록) 건물 그림자가 도로를 덮을 가능성이 높다고 추정하는 방식으로 그늘 여부를 판단했습니다.

### 4. 오래된 공공데이터 문제 → "저장해두기" 대신 "그때그때 물어보기"로 전환
편의점 공공데이터가 최대 1년 전 기준이라, 이미 문을 닫은 곳도 계속 지도에 표시되는 문제가 있었습니다.

**처음 시도한 방법**: 카카오 지도 API로 "이 위치에 진짜 편의점이 있는지" 하나하나 대조 검증하는 방식을 만들었습니다. 그런데 실제로 돌려보니, "반경 안에 편의점이 하나라도 있으면 통과"하는 방식이다 보니, 문 닫은 특정 매장 대신 근처의 다른 매장이 잡혀서 "있다"고 잘못 판정하는 경우가 많았습니다.

**최종 해결**: "우리 DB에 미리 저장해두고 나중에 검증"하는 방식 자체를 버리고, **사용자가 편의점을 찾을 때마다 카카오 지도 API에 바로 물어보는 방식**으로 바꿨습니다. 데이터를 미리 저장해둘 필요가 없어지니 "오래된 정보"라는 문제 자체가 사라졌고, 코드도 오히려 더 단순해졌습니다.

이 과정에서 예상 못 한 버그도 하나 발견했습니다: 원래는 다른 파일(DB 연결 파일)을 거치면서 "우연히" 환경변수(비밀키 등)가 먼저 로딩되고 있었는데, 그 파일을 안 쓰게 되면서 이 우연한 순서가 깨져 API 키를 못 읽어오는 문제가 생겼습니다. 각 파일이 자기가 필요한 환경변수를 스스로 안전하게 불러오도록 고쳐서 해결했습니다.

### 5. 로컬에선 잘 되던 기능이 배포하니 시간이 안 맞았던 문제
실시간 기온 표시 기능을 붙일 때, 로컬 PC에서 테스트할 땐 정상이었는데 Render에 배포하자 항상 9시간 전 기온이 나오는 문제가 있었습니다. 원인은 서버가 기준으로 삼는 시간대였습니다 — 로컬 PC는 한국 시간대(KST)로 설정되어 있어서 문제가 안 보였는데, Render 서버는 기본값인 UTC 시간대로 동작해서 "지금이 몇 시인지"를 9시간 어긋나게 계산하고 있었습니다. 서버가 어떤 시간대로 설정되어 있든 항상 한국 시간 기준으로 계산하도록 코드를 고쳐 해결했습니다. 로컬 환경과 배포 환경의 차이 때문에 생기는 문제를 직접 겪어본 경험이었습니다.
